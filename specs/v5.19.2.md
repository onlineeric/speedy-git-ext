# v5.19.2 — Settings button sometimes opens a new graph instead of VS Code Settings

**Status:** diagnosed and fixed 2026-10-15 (shipped in 5.19.2). **Target:** 5.19.2 (patch release).
**Scope:** one behavioural fix in `src/ExtensionController.ts` plus tests, docs, changelog and version
bump. No webview changes, no new RPC, no telemetry catalog change.

## Symptom (user report)

With Speedy Git 5.19.1 on VS Code 1.141.x, clicking the toolbar **Settings** button did not open VS Code
Settings. Instead a new graph tab appeared, exactly as if **New Tab** had been clicked. It happened on
several clicks in a row. About 5 minutes later, without restarting VS Code, it worked normally again,
and it could not be reproduced on demand afterwards.

## Root cause — summary

The **split-editor auto-fill** (shipped in 5.17.0, `utils/editorSplitFill.ts` + `ExtensionController`)
mistakes VS Code 1.141's **modal Settings editor** for "the user split a graph editor". It then fills the
modal's editor group with a new graph, which opens on top of Settings. The one safeguard, re-reading the
group after a single `setTimeout(0)`, is a timing race. That makes the bug intermittent.

The Settings button itself is correct: `rpcClient.openSettings()` →
`vscodeCommandHandlers.openSettings` (`src/webview/handlers/vscodeCommandHandlers.ts:9`) →
`workbench.action.openSettings('speedyGit')`.

## Chain of events (verified against VS Code 1.141.0–1.141.2 source)

1. **VS Code opens Settings in a modal editor part.** 1.141 adds the setting
   `workbench.editor.useModal` (`off` | `some` | `all`). Its default is `"some"`, and an experiment sets
   it at startup (`experiment: { mode: "startup" }`). `preferencesService.getEditorGroupFromOptions`
   returns `MODAL_GROUP` (`-4`) whenever `useModal !== "off"`, so Settings opens in a modal overlay
   instead of the active editor group. Per the setting's own description, `"some"` covers "certain
   editors such as Settings and Keyboard Shortcuts". `"all"` opens every editor in the modal.

2. **The modal's group is announced empty, and its editor arrives afterwards.**
   `EditorParts.doCreateModalEditorPart` creates and registers the part, then calls
   `this._onDidAddGroup.fire(part.activeGroup)` while that group is still empty. The editor is added
   only after that: `findGroup` resolves through `.then(a => a.activeGroup)`, `editorService.openEditor`
   awaits it, and then `group.openEditor(settingsInput)` → `EditorGroupView.doOpenEditor` →
   `model.openEditor(...)` runs.

3. **The extension host gets two separate messages.** `MainThreadEditorTabs` handles
   `onDidAddGroup` with `_createTabsModel()`, which sends `$acceptEditorTabModel(fullModel)`. The modal
   group is in that model with **0 tabs**. The Settings tab follows later as a separate
   `$acceptTabOperation` (OPEN). The modal group counts as a real tab group:
   `editorGroupsService.groups` includes every part, and its `viewColumn` is its index in
   GRID_APPEARANCE order across all parts, with main-part groups first. With one main group, the modal
   group is `ViewColumn.Two`.

4. **Our listener treats it as a split.** In the extension host, `$acceptEditorTabModel` fires
   `onDidChangeTabGroups({ opened: [modalGroup] })`. In `registerSplitEditorFill`
   (`src/ExtensionController.ts:245`), `source` is the last active group, which is the graph's group,
   since the user just clicked inside the graph. `pickSplitFillGroup` (`src/utils/editorSplitFill.ts:44`)
   returns the modal group because it is empty and in a different column.

5. **The one-tick re-check races.** `fillSplitGroup` (`src/ExtensionController.ts:269`) runs
   `await new Promise((resolve) => setTimeout(resolve, 0))`, which Node clamps to about 1 ms, and then
   checks `group.tabs.length > 0`. If the Settings OPEN message has not been processed yet, the group is
   still empty, and it calls `createTab(repoPath, group.viewColumn, 'splitEditor')`.

6. **The graph lands inside the modal.** `createWebviewPanel` passes that `viewColumn`. The main thread's
   `columnToEditorGroup` resolves it with `getGroups(GRID_APPEARANCE)[index]`, which is the **modal
   group**. The new graph becomes the modal's active editor, on top of Settings. To the user it looks
   like New Tab.

**Why it is intermittent:** the outcome depends only on whether the second message is processed
within that ~1 ms. When the renderer or the extension host is busy, or a remote transport (WSL/SSH)
delivers the two messages in separate reads, the check loses repeatedly. When the machine is idle, it
wins. That fits "several failures in a row, then normal 5 minutes later, no restart".

## Blast radius

- Toolbar **Settings** button, and the date-format gear in the commit table header
  (`webview-ui/src/components/CommitTableHeader.tsx:201`). Both use the same `openSettings` RPC.
- Anything VS Code opens modally while a graph tab is focused: `Ctrl+,`, Keyboard Shortcuts, extension
  details, release notes.
- With `useModal: "all"`, any editor opened while a graph is focused, presumably including files and
  diffs opened from the graph. *Not verified in code; check during manual testing.*
- The existing case of dragging a tab into a new group (the reason the tick wait exists) relies on the
  same race, so it can also misfire under load.

**User workaround until the fix ships:** `"workbench.editor.useModal": "off"`.

## Making the bug deterministic (to confirm the diagnosis before fixing)

Temporarily remove the tick wait from `fillSplitGroup`, so the group is checked synchronously inside
the event. Every Settings click with a graph focused then opens a graph inside the modal, because the
group is always empty at that moment. Revert afterwards.

To check after the fact on an affected machine (VS Code not restarted): look in the **Speedy Git**
output channel for `Showing git graph (N open)` at the time of the click. `createTab` logs it. In
telemetry, `panelOpened` with trigger `splitEditor` counts these. Use it to compare before and after the
release.

## Fix

### Approach: replace the timer with one round trip to the workbench

In `fillSplitGroup`, replace `setTimeout(0)` with an awaited main-thread RPC, then re-read the group.

**Why this is deterministic and not just a longer wait:**

- The extension host and the workbench talk over **one ordered RPC channel**.
- In 1.141, the group-add message and the Settings tab's OPEN message are sent within **one renderer
  task**. Between `_onDidAddGroup.fire` and `model.openEditor` there are only microtask awaits (verified
  in `doCreateModalEditorPart`, `editorService.openEditor`, `EditorGroupView.doOpenEditor`).
- Our request reaches the renderer after that task has finished, so the OPEN message was already sent.
  The reply is queued behind it. When our `await` resumes, `group.tabs` already contains Settings, and
  the fill is skipped.
- A real split of a webview leaves the group empty, because VS Code cannot duplicate a webview. It is
  still empty after the round trip, so it is still filled. Behaviour for real splits is unchanged.
- A tab dragged into a new group is also added within the same renderer task as the group, so the
  existing drag rule becomes deterministic as well.

**Which call:** `vscode.commands.getCommands()`. Verified: `ExtHostCommands.getCommands` →
`#proxy.$getCommands()` → `MainThreadCommands.$getCommands` returns
`Promise.resolve([...CommandsRegistry.getCommands().keys()])`. It has no side effects. Its cost, one
list of command ids, is paid only when a group opens empty while a graph is focused, which is rare.
Ignore the result. If the call fails, fall through to the check as it stands today.

### Code sketch (`src/ExtensionController.ts`)

```ts
private async fillSplitGroup(group: vscode.TabGroup): Promise<void> {
  await workbenchCaughtUp();
  // Closed meanwhile (a modal dismissed at once), or something landed in it: not a split.
  if (!vscode.window.tabGroups.all.includes(group) || group.tabs.length > 0) return;

  const repoPath = this.mostRecentlyActiveTab()?.topLevelRepoPath ?? this.savedDefaultRepo();
  if (!repoPath) return;

  await this.createTab(repoPath, group.viewColumn, 'splitEditor');
}
```

```ts
/**
 * Resolves once every tab change the workbench sent before this call has been applied.
 *
 * VS Code announces a new group before putting anything in it: the modal Settings editor
 * (`workbench.editor.useModal`, 1.141+) and a tab dragged into a new group both arrive as
 * "group opened, empty" followed by a separate "tab opened". The two are sent in one
 * workbench task and the extension-host channel is ordered, so a reply to any request we
 * send now arrives after the tab. A timer is NOT a substitute: it loses exactly when the
 * machine is busy, which is how a Settings click turned into a new graph (v5.19.2).
 */
async function workbenchCaughtUp(): Promise<void> {
  // Only the ordering matters; a failure leaves the group to be read as it stands.
  await vscode.commands.getCommands().then(noop, noop);
}
```

- Pick the name and the `noop` helper to match the file's style. A bare `() => undefined` is fine.
- The `tabGroups.all.includes(group)` guard is optional but cheap: a group that closed during the round
  trip must not get a graph created at its old column. `ExtHostEditorTabs` keeps stable `apiObject`
  instances, so `includes` identity works.
- Rewrite `fillSplitGroup`'s doc comment, which currently explains the "re-read a tick later" for
  dragged tabs, so it describes the round trip and names both the modal and the drag cases.
- `src/utils/editorSplitFill.ts` and `pickSplitFillGroup` do **not** change. The rule is right; only
  the wait was wrong.

### Alternatives considered and rejected

- **Longer timeout (50–100 ms):** still a race, and it fails under exactly the condition that caused
  this bug, a busy machine. It also delays every real split fill.
- **Suppress the fill only while our own `openSettings` handler runs:** misses `Ctrl+,`, Keyboard
  Shortcuts, extension pages, `useModal: "all"`, and the date-format gear unless that is wrapped too.
- **Recognise the modal group:** the `TabGroup` API exposes no part or modal information. The modal's
  `viewColumn` is simply the next column, so it cannot be told apart from a split to the right of the
  last group.
- **Pass a `groupId` to `openSettings`** (VS Code honours it over the modal): extensions cannot get
  editor group ids, and it would fix only our button anyway. Changing the user's `useModal` setting is
  off-limits.

## Tests

`src/__tests__/ExtensionController.tabs.test.ts`, `describe('splitting a graph editor')`:

- The `vscode` mock has **no `commands`** today. Add `commands: { getCommands: vi.fn(...) }`, backed by
  a hoisted deferred promise, so each test decides when "the workbench answers". Reset it in the
  existing `beforeEach`.
- Keep the three existing tests passing: fills an empty split, ignores a split of a non-graph editor,
  ignores a group a dragged tab landed in. Their `await new Promise(setTimeout 0)` waits also need the
  deferred resolved, or `vi.waitFor` on the outcome.
- **New regression test, which must fail against the current code:** "leaves a group alone when its
  editor arrives after a tick but before the workbench answers". Fire `opened` with an empty group, then
  `await` a `setTimeout(0)` and assert no second graph yet. Push a non-graph tab into the group, as the
  Settings tab arriving late, resolve the deferred, and expect `tabState.created` to stay at length 1.
- **New:** "still fills a split when the group is empty once the workbench answers".
- **New, if the guard is added:** "does not fill a group that closed before the workbench answered".
  Remove it from `editor.state.all` before resolving.
- Verify the regression test catches the bug: temporarily put the `setTimeout(0)` back and watch it
  fail.

## Docs, release and telemetry

  Tabs*: replace "it re-reads the group a tick later so a tab *dragged* into a new group keeps it" with
  the round-trip rule. VS Code announces a new group empty before its editor arrives (modal Settings in
  1.141+, dragged tabs), so the fill re-reads the group after one workbench round trip, never after a
  timer. An agent must not "simplify" it back to `setTimeout`.

  > - **Settings no longer opens another graph instead.** VS Code 1.141 opens Settings in a pop-up
  >   (modal) editor. Speedy Git took that pop-up for a split of the graph editor, which it answers by
  >   opening another graph, so clicking **Settings** in the toolbar could show a new graph on top of
  >   Settings. The same applied to the date-format gear, `Ctrl+,` and Keyboard Shortcuts while a graph

## Verification

1. `pnpm typecheck`, `pnpm lint`, `pnpm test`.
2. Manual test via "Run Extension" on VS Code 1.141+ with `workbench.editor.useModal` at its default:
   - With a graph focused, click toolbar **Settings** about 10 times. Settings opens in the modal every
     time, and no extra graph appears.
   - The date-format gear in the commit table header behaves the same.
   - With a graph focused, press `Ctrl+,` and `Ctrl+K Ctrl+S`. No extra graph appears.
   - **Split Editor Right**, `Ctrl+\` and split down on a graph each still open a new graph in the new
     group.

     appears.
   - Set `workbench.editor.useModal` to `"all"`, then open a file and a diff from the graph. No extra
     graph appears.
   - Set `workbench.editor.useModal` to `"off"`. Settings opens in a normal tab, and splits behave as
     before.
